# NIMO UI Parity — Decisions and Exceptions

Migration note (2026-08-31): this ledger remains visual-history evidence.
React/Tauri NIMO is now the primary product UI; references below to PySide as a
source of truth mean frozen comparison evidence, not the default product or a
requirement to implement new interactions there first.

## Scope lock

Phase 1 is a React + TypeScript + Tauri visual migration. It uses the existing
PySide6 UI as the source of truth and intentionally does not modify the Python
pipeline, model routing, project storage, `.env`, or provider credentials.

## Boundary decisions

| Decision | Rationale | Phase 1 consequence |
| --- | --- | --- |
| Pages use only `@nimo/engine-contracts` | The same UI must later run against a local sidecar and a cloud backend. | No React page imports `novel_forge/`, reads `.env`, or calls a Provider directly. |
| Use `MockEngineClient` only | This phase is visual/interaction parity, not an engine migration. | Every operation changes in-memory UI state or renders an explanatory Mock result. |
| Store UI preferences separately | User interface state must not be conflated with project data or credentials. | `UiSessionStore` persists only active page and side-rail collapse state. |
| Preserve source SVG for all NIMO marks | Brand geometry must not diverge between web, Tauri, and macOS. | The web mark and the runtime window icon both derive from `nimo-symbol.svg`; the semantic logo token controls their color. |
| Theme palette mirrors PySide6 semantic tokens | Local CSS literals create drift across five themes. | Token names are retained through the React theme projection and set as CSS custom properties. |
| Typography follows rendered scale, not literal Qt units | Qt QSS describes normal top-bar type in points (`22pt` title, `13pt` body/action), while React uses CSS pixels. | Source-sized dialog fixtures retain their measured readable scale; the shared product chrome deliberately uses smaller CSS pixels. Any density change must be compared from same-size source/target frames, not inferred from the QSS number. |
| Compact desktop chrome is an explicit product preference | The user requested a smaller overall UI, button labels and more primary information at 1440×900. | Shared product geometry is owned by the `4/8/12/16/20/24px` spacing scale and `10/11/12/13/16/22/24px` type scale. The default control is 32px/12px; 28px/11px is reserved for dense strips and 36px/13px for measured source dialogs. Generic `AppDialog` chrome uses a 19px title, 12px description and compact 21px inset so document/form content owns more of the viewport; source-sized parity fixtures may retain their measured geometry through a dedicated class. Document text, semantic hierarchy, component states and interactions remain unchanged. This is a documented visual exception to literal old-client typography parity. |
| Native window and surface shape share a compact radius hierarchy | The user requires a rounded, polished desktop frame without turning the workbench into a loose “card wall.” | Tauri keeps its decorated opaque native window for real macOS outer rounding. The WebView uses `18/14/17/12/8–10/999px` window/shell/surface/card/control/pill tokens; source-sized dialogs select a measured token rather than adding arbitrary radii. Theme changes never alter geometry or control height. |
| Project-reader dirty navigation is an ordered session boundary | The source protects in-progress final revision, outline polish and character changes before project switching; spreading this logic across three widgets would drift as the reader grows. | A transport-neutral `ReaderUnsavedSession` registry records source order and page-specific action labels, while each workbench retains only its own save/discard behavior. `SourceMessageDialog` is measured against the 440×147 source generic dialog and shares the compact dialog-radius token. The source native question icon remains an explicit native-capture comparison item; no handwritten substitute is introduced. |
| Motion is an enhancement layer, not an information layer | The new architecture may improve feedback, but the user prioritises compact, stable creation surfaces. | Page changes use a short opacity transition; focus/hover responses remain CSS-native; overlays stay viewport-fixed; all nonessential motion disables under `prefers-reduced-motion`. `motion-system.css` is the sole cross-surface owner of press, active-step and checking-pulse feedback, so stable source fixtures remain unaffected. No action, progress or streamed content depends on animation to be understandable. |
| Overlays belong to the application viewport | Page transitions and long workbenches use transforms and independent scrolling; a fixed overlay nested inside either becomes relative to that ancestor and can open outside the visible window. | `OverlaySurface` portals every modal and non-modal tool to `document.body` while React keeps event ownership, Escape handling, focus trapping/restoration and theme inheritance intact. Individual dialogs own only their source geometry and semantics. |
| Narrative visuals use typed data plus pure geometry | Relationship and timeline screens need to remain stable across themes, reloads, fixtures and later transport changes. | `NarrativeVisualizationView` carries render data; `narrative-visualization-layout.ts` owns deterministic coordinates; SVG components own interaction only. |
| Start with SVG, retain a renderer seam | Current project graphs and timelines are medium-density and must be inspectable and accessible. | A future Canvas/WebGL adapter can replace the renderer without changing view models, layout tests or engine adapters. |
| Stream detail has one renderer | Embedded observation and detached windows must remain consistent after reconnects and stream replays. | `TaskStreamState` remains the event boundary; `TaskStreamDetail` owns order and thought folding; window placement is presentation-only. |
| Workflow form mutations are Engine-owned | Preset CRUD, AI field generation and creative-note history are shared project data, so a second client-local source would diverge from PySide6. | `LongInitFormPanel` and `WorkflowAiAssistant` keep only unsaved form drafts and selection state; all durable operations use versioned Engine commands and refresh authoritative data. |
| Chapter destructive actions are intent-only | Cleanup, regeneration and project switching have material effects in the Python desktop application. | Phase 1 renders their range, warning and checkpoint-preservation semantics, but changes only the selected UI state and an in-memory notice. |
| Voice-team rebuild is a selected local session | The source rebuild action excludes the work-level narrator, applies only to checked roles, and must preserve all other voice assignments. | `VoiceRebuildDialog` owns only an in-memory selection and result notice; it cannot change a provider, audio file, or persisted voice assignment. |
| Voice script direction is staged by contract depth | A segment editor needs rich TTS direction before the current `VoiceScriptSegmentView` is allowed to transport it. | Text, speaker and emotion are the only existing contract fields that become local pending-review output; tone, timing, pronunciation and platform notes remain reversible front-end draft metadata until a versioned command is designed. |
| Performance direction never reuses the source-script save channel | The native voice room edits a candidate take and must not overwrite the formal dubbing script. | `VoiceScriptEditorDialog` has an explicit `performance` mode. Its save result carries the local draft map while returning the original `VoiceScriptSegmentView[]`; this makes source-script preservation mechanically testable. |
| Voice-room review uses an explicit take state machine | The source rejects an old candidate when its guidance changes; it only promotes a generated candidate after explicit acceptance, and chapter reassembly remains separate. | `voice-room-session.ts` owns `formal → guidance_saved → generating → candidate → accepting → accepted`, with a discard transition that never changes the formal script. Phase 1 keeps this in memory; a future Engine command replaces only the transition driver. |
| Voice design runs through a local state machine | The native brief dialog precedes an asynchronous, provider-backed design/preview operation, but Phase 1 cannot call a provider or write a voice profile. | A pure draft/run/result reducer owns validation and retry states; only an explicit “apply” projects a voice label and review state into the React cast session. The brief is not overloaded into an existing contract field, so a future EngineClient command can replace the timer without rewriting the UI. |
| Voice cloning keeps media out of the UI state | Voice cloning requires a reference file and, for some platforms, explicit authorization and a transcript; Phase 1 must not read or upload media. | The local-file path retains only the selected filename, while the provider path retains only its File ID. Authorization is modeled explicitly before a local run state; a future protected EngineClient upload command must own media bytes, consent audit data and provider IDs. |
| Provider File-ID prompt follows the small Qt input-dialog primitive | The source provider path is a 420×200 `show_text_input_dialog`, with no duplicate content title, an autofocus File-ID field and a disabled confirm action until text exists. | A restricted parity URL is the only way to start this state. `VoiceCloneDialog` reuses the shared overlay/focus boundary but adopts the measured source geometry and button semantics; a normal “上传克隆” action still resets to the local-file route. |
| Voice delivery shares an operation presentation only | Assembly and export are distinct workers in the native app, but both expose configuration, active progress and a result state. | `VoiceDeliveryDialog` reuses the generic visual operation timeline while retaining separate step maps and labels. It creates no file and can later receive a common EngineClient task stream without conflating assemble/export commands. |
| Model profiles and routes use a credential-isolated local draft | The source Settings page visibly contains an API-Key row, but Phase 1 must not read existing secrets or persist a new one. | The shared source-shaped form keeps a typed API-Key submission value only while the form is open; `ModelProfileView`, React session persistence and notices never receive it. `TaskRouteView` carries stable task keys, hints, subgroups, ordered fallback entries and optional temperature semantics. Profile CRUD, connection feedback and group/subgroup routing remain reversible front-end state until protected EngineClient commands exist. |
| Settings navigation has a hard performance boundary | The PySide6 火候 page may build status cards, deferred sections, route controls and probe results around activation; that coupling is a known switch-time risk. | The React shell renders a lightweight settings fallback, prefetches only code and a sanitized snapshot after idle, and loads the route workbench only when its **inline** section opens. While routing is focused, it suppresses the unrelated overview and status-card grid so the source-shaped route matrix owns the viewport. It never begins connectivity work because the page became active. A future EngineClient connectivity command must be cancellable, emit background task progress, cache by configuration revision, and invalidate explicitly after profile/routing changes. |
| Model-card expansion is a non-urgent render | “检测全部通路” can expose a large card set, and expanding it must not delay cancel/navigation feedback. | `ModelConnectionStatus` uses React `startTransition` for the optional expansion, retains the first 12-card fast path, and asks supporting WebViews to skip offscreen card paint/layout via `content-visibility` with a stable 114px intrinsic size. The interaction text and card geometry stay source-shaped. |
| AI generation failures are fixture-driven in Phase 1 | A commercial async surface needs an observable error state before it has a provider adapter, but the source forms do not expose a failure simulator. | A restricted parity fixture freezes the source-shaped failure acknowledgement. It preserves fields and performs no model call; a future EngineClient stream will own retry policy rather than a second UI-only retry path. |
| Documents are parsed into typed display blocks | A later cloud/local transport must not force HTML into the UI or make untrusted report text executable. Long Chinese prose also needs a stable reading measure, while large nested artifacts must not mount thousands of hidden nodes. | A pure renderer parses Markdown and JSON into safe data blocks; React owns one typography system and source-shaped structure/raw controls while `RenderDocumentView` remains the only document boundary. Nested JSON collections render their children only after expansion, so local and future cloud payloads share the same bounded initial render path. |
| Local document actions require resolved metadata | A display label can be a relative path, virtual `session://` URI or future cloud object key; treating it as an operating-system path would make “在文件夹中显示” incorrect and unsafe. | `RenderDocumentView.localPath` is a separate optional engine-owned capability. The button is disabled without it; Tauri canonicalizes and verifies the path before invoking the platform file manager. Size and modification labels follow the same optional metadata boundary, with UTF-8 size derivation only as a display fallback. |
| Chapter memory is a typed inspector, not page-owned cards | The source `UnifiedMemoryPanel` groups context by a stable tab taxonomy and already owns the density/motion model. | `ChapterMemoryTabView` and `ChapterMemoryCardView` keep the data boundary transport-neutral; one reusable React inspector owns selection and presentation, avoiding separate card layouts for prepared, checkpoint and later running states. |
| Native builds watch generated frontend assets | Tauri embeds Vite's hashed `dist/` assets, but Cargo otherwise only watches Rust and Tauri configuration. | `src-tauri/build.rs` recursively emits `rerun-if-changed` entries for `dist/`, preventing a native package from keeping an obsolete asset manifest and opening a white WebView after a frontend rebuild. |

## Explicit non-goals

- Calling real LLM, TTS, embedding, or Provider APIs.
- Writing project files or modifying existing Python desktop behavior.
- Reading API keys, environment variables, or `model_profiles.json` from React.
- Claiming pixel parity without a same-fixture, same-viewport comparison.

## Current visual evidence policy

The existing `tests/desktop/baselines/` PNGs are treated as PySide6 evidence,
not as automatic proof that the React version matches. The React client has
manual browser evidence for the primary page flows, while repeatable cross-app
pixel comparison remains a Phase 1 exit requirement. `verification-matrix.md`
records that distinction explicitly.

The Chromium runner starts its own strict-port `127.0.0.1:1427` Vite server
for each run and never reuses a developer server on the normal Tauri port.
This keeps worktree-local screenshot baselines from being silently generated
against a different checkout. Intentional baseline updates regenerate all
frames and require PNG-diff review; they remain regression evidence only.

PySide6 golden capture waits beyond `DENSITY_RESIZE_DEBOUNCE_MS` after the
target viewport is shown. This prevents a regular 1440×900 window from being
captured during its 264px compact-rail transition; the stable source frame is
the only valid comparison target.

## Approved interim differences

| Surface | Difference | Why it is interim | Exit condition |
| --- | --- | --- | --- |
| Primary-page populated fixtures | React uses fixed semantic fixture content rather than reading real local projects. | Phase 1 prohibits a Python bridge. | Fixture data and source screenshots are frozen per state, then visually compared. |
| Chapter Studio prepared viewport | The Qt source can clip trailing controller/inspector content at its current effective width; React keeps the same controls in a horizontally scrollable compact strip and preserves the main three-column content. | The user explicitly prioritised the main information window over reproducing non-semantic clipping. | Same-state PySide6/Tauri comparison verifies control hierarchy, spacing and content geometry; no visual acceptance is claimed before that diff. |
| Shared shell and dense page chrome | React intentionally reduces the old client’s rail/top-bar/button geometry, so a full-frame pixel diff includes an approved density mismatch even when content semantics are correct. | The user explicitly prefers a compact, information-first workbench. | Continue visual diffs as diagnostics; enforce strict 0.25% component acceptance for source-sized dialogs and source-sized controls. Whole-frame sign-off for a compact-primary page requires a recorded hierarchy/interaction review rather than the old-size 0.75% threshold. |
| Project action effects | Directory, vector rebuild, deletion and export actions are Mock-only. | They must not mutate current user data during UI migration. | Replace `MockEngineClient` with the Phase 2 local sidecar adapter. |
| Visual threshold | No page is marked pixel-accepted yet. | Automated same-platform capture/diff is not yet present. | Default-theme difference ≤ 0.75%; component difference ≤ 0.25%, or documented approval. |
