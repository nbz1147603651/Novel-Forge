## 2. 根因结论

### 2.1 小说终稿到配音的来源边界不够强

章节归档会产生 TTS 元数据，但旧结构没有携带章节号和终稿文本哈希。配音侧因此只能
“相信文件名和存在性”，无法判断元数据是否来自当前终稿。章节重写后，旧提示可能继续
流入配音脚本，形成隐蔽的数据断层。

同时，长篇 DRAFT 阶段仍接收原始 Bridge 卡片，和已经吸收到
`ChapterPlan.opening_bridge` 的可执行锚点形成双来源。两个来源一旦不同步，模型无法知道
哪个字段才是权威输入。

修复原则：

- TTS 元数据必须绑定 `chapter_number + source_text_hash`。
- 配音只消费与当前章节终稿匹配的元数据；不匹配时明确丢弃。
- Bridge 只保留为血缘/审计产物；DRAFT 只消费 Plan 中已经吸收的 opening bridge。

对应提交：`4b2c22dd refactor(novel): bind TTS metadata to final chapter source`

### 2.2 脚本并行阶段按数组位置合并，破坏稳定身份

脚本专业审校与口语化改写并行执行，旧合并方式按列表偏移量拼接结果。这隐含假设两个
分支不会插入、删除或重排段落，也会让口语化结果覆盖专业审校已经修改的
`spoken_text`。同一问题延伸到说话人修复：持久化的 `segment_index` 被当作数组下标，
非连续 ID 会修错段。

修复原则：

- 段落以持久 `segment_index` 为身份，以 `segment_uid` 为内容版本。
- 并行结果只按稳定身份合并；身份集合不一致时安全失败。
- 专业审校修改过的口语文本优先；只有审校未修改时才采纳并行口语化结果。
- 任何会改变合成输入的人工修复都刷新 UID。
- 修复后同时清理机器裁决与专业审校中的未决列表。

对应提交：`9f23b18e fix(tts): make script repair identity-safe and transactional`

### 2.3 写入与派生音频失效顺序相反

脚本重新生成、PySide 手工保存等路径先删除或标记音频失效，再写入新脚本。如果脚本写入
失败，用户会同时失去可用旧音频和新脚本，回滚锚点不存在。

修复后的统一顺序是：

1. 构造并验证完整的新脚本；
2. 原子写入新脚本；
3. 写入成功后才失效旧音频、进度和合成结果。

说话人修复持久化失败时返回原脚本，不把未持久化的内存对象伪装成成功结果。

### 2.4 人工说话人审阅只在界面存在，没有完整后端写链

React Engine 读模型没有输出 `needsSpeakerReview` 和稳定 `segmentIndex`，真实引擎下弹窗
不会出现；前端命令又缺少 legacy client 与 API 端点。即使弹窗出现，旧实现仍用数组位置
读取上下文，并在部分提交后清空全部未决段。

本轮补齐了完整链路：

`读模型未决状态 → 稳定段 ID → React 决策 → Engine command → API → 工作区项目锁
→ 角色合法性校验 → 原子写脚本 → 派生音频失效 → 刷新读模型`

部分提交只清除已经解决的 ID；网络或后端拒绝时弹窗保留，并展示错误，不再制造“看似已
处理、实际未落盘”的状态。

### 2.5 完整度门禁把短旁白和非发声提示当成情绪失败

旧情绪分化率用所有脚本段作为分母，静音、音乐、音效会稀释比例；对 1–2 个发声段应用
15% 阈值，实际等价于强制 50%–100% 段落带情绪，平静短旁白必然失败。

修复后只统计可发声段，并在样本少于 3 段时不执行百分比硬判。长脚本的原阈值保持不变，
因此没有用全面放宽质量门槛掩盖短文本问题。

## 3. UI 与交互审计

### PySide Voice Studio

- 屏幕上的“第 N 段”改为人类可读的连续序号，内部仍传递持久段 ID。
- 审阅提示按脚本签名缓存，只在顺序、未决集合或审阅状态变化时重新计算，降低重复渲染。
- 音色变化仍会触发必要的重新润色，不牺牲准确性。
- 手工脚本保存采用“先原子写入、后失效音频”。
- 新增非连续段 ID、写入失败保留旧音频等回归测试。

### React 桌面端

- 项目或章节切换时立即清空旧章节/旧 Voice Studio 状态，并忽略过期异步响应。
- Voice Studio 用 `projectId + chapterNumber` 作为实例边界，避免跨项目残留。
- 说话人弹窗改用稳定段 ID 查找上下文，支持部分提交和失败重试。
- 长列表使用独立滚动区和 `content-visibility`，避免大量段落同时参与布局。
- 补齐响应式双栏/单栏布局、选中态、错误态和候选角色信息层级。
- 删除 5 个从未接入路由、类型已过期且导致构建错误的重复 Tab 脚手架，保留唯一真实实现。

React 改动遵循稳定 primitive effect 依赖、异步取消保护、以 key 重置局部状态和长列表减少
布局工作的原则。

对应提交：`1ef56824 feat(voice): close speaker review contract end to end`

## 4. 修复后的权威数据流

```text
小说章节终稿
  └─ Finalize
      ├─ 归档 chapter markdown
      └─ 生成带 chapter_number/source_text_hash 的 TTSMetadata
          └─ 配音上游投影校验当前终稿哈希
              └─ 脚本生成（稳定 segment_index）
                  ├─ 专业审校 ─┐
                  └─ 口语化改写 ─┴─ 按稳定身份合并
                      └─ 完整度门禁
                          └─ 人工说话人裁决（可选）
                              └─ 原子脚本写入
                                  └─ 失效旧音频/进度
                                      └─ 合成与装配
```

全链路现在遵守四条不变量：

1. 小说侧只有终稿及其有界投影能够进入配音。
2. 段身份和屏幕序号分离，所有写操作使用稳定身份。
3. 任何下游派生物只能在新上游成功持久化后失效。
4. UI 成功状态必须来自后端已持久化结果，不接受仅内存成功。

## 6. 后续边界

本轮没有重写整个小说生成系统，也没有把高频变动文件一次性拆成全新子系统；这种大范围
结构迁移会扩大验证面。建议后续沿以下顺序继续：

1. 将 `workspace/tts_ops/execution.py` 继续按 read model、command、artifact transaction
   拆分，保持现有门面兼容。
2. 为小说各阶段逐步引入和 TTS 相同的来源哈希/版本字段，优先覆盖可恢复检查点。
3. 将 Engine 命令的 accepted/rejected 结果抽成统一 envelope，减少各页面重复错误处理。
4. 在全仓依赖升级时处理 Starlette TestClient 弃用项。

这些是后续可维护性工作，不是本轮已发现链路的未修阻断问题。
