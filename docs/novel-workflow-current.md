### B5 当前实现（依赖 B4 `84045ddb`）

- `AuthoringWorkspace` 在 NIMO 阅卷/章台保留原内容区，提供默认收起的共创侧栏；阅卷保留原浮动入口，章台则将入口收入“章台工作台”标题动作组，与“阅卷 / 回机杼”导航动作分组，不再用绝对定位叠在业务页头上。短篇和不支持能力的客户端不出现入口。保存策略、启用授权、准备本章和启动章段各自独立，旧自动偏好不能替代新授权。
- 七种讨论上下文对应规格、世界、人物、蓝图、大纲、章节和报告；`AUTHORING_CHAT` 输出结构化答复、候选和白名单建议。仅显式勾选本轮操作后才执行准备或已批准提案。聊天不写正史，重放复用答复和确定提案编号；拒绝后不复活提案或自动生成替代案。
- 提案展示原文/候选、依据、影响章段、费用风险和锁定提醒；编辑后重新批准，接受在确认对话框核对具体版本，再调用已有领域入口。当前可应用范围仍是检查点、正文修订和已验证补纲候选；设定/蓝图讨论不伪装成可应用编辑。
- N07–N10 的最终检查如果改变已验收正文，保存新检查点，要求作者验收新版本；新候选尚未成为正式正文/正史。保存精确细化哈希，验收该版本后不再次进行可选的终端人性化，但事实及一致性门禁继续运行。
- 必需任务确认携带 `approval_version`，NIMO/HTTP/PySide 均传递显示版本；旧客户端漏传或过期时等待，不使用默认项。连跑的执行末章按授权截断，但全书总目标不缩水。
- 取消记录不等于后台已安全退出：作者状态区分正在安全停止/已停止，停止期间不能重新启用策略。
- 验证：129 项相关 Python、105 项 API/job 消费者、616 项 Vitest、TS、mypy 基线、架构与中英文/兼容提示词包检查通过。未调用真实模型、未修改作品数据，实际浏览器交互仍待 B7。
- 未关闭的缺口：完整领域修改接入、更紧预算联动、应用中断恢复、交付过期关系和回退演练。`authoring_coauthor` 保持关闭；不是“完整共创已发布”。回退先暂停任务并等待安全退出，再逆序 revert，保留候选、批准和费用证据。

### B6 当前实现（依赖 B5 `fc655e68`）

- N12 人工改稿继续走 `execute_manual_revision`：已有 `final_revision_versions` 元数据扩展为提交日志，保存修改前/后正文、输入哈希及被失效化产物的副本和哈希；正式写入前标记过期。备份阶段可暂停，短暂合法提交阶段完成后停止。
- 正文已经写入但应用状态未写完时，`recover_committed_revision` 只核验当前哈希并补完提交结果；不重复清理下游，不改后来新增的章或作者新稿。未能证明提交的候选仍须原有版本/批准检查。界面提供“核验已提交结果”，不是重新授权。
- 历史正文通过 `restore_chapter` 生成比较提案，专项批准后写成新修订。拒绝、取消、过期不会恢复作品，保存的候选和备份证据不删除。范围仍是单章正文；状态/报告重新失效，不能把旧正史快照复制回来。
- 阅读报告携带 `freshness` / `freshness_message`，区分当前、过期和缺少哈希证据；已有分数不能代替当前正文验证。交付投影只把有明确修订证据的上游变化计为新阻塞，不把旧项目缺少状态水位误判为新修订。

### 全书规划与“只能十章”

- 新初始化请求默认全书规划：分批覆盖目标总章数，而非要求一次模型调用输出全书。显式保存的旧 `progressive` 请求不自动改成 `full`。
- 渐进规划首次生成前 `min(10, 总章数)` 章的大纲，细化前 `min(5, 总章数)` 章的设计与契约。全书宏观蓝图仍面向全书。
- `planned_through_chapter` 表示已有规划的范围；`hard_through_chapter` 表示已细化、可供执行的承诺范围。**hard 不等于“作者已经逐章批准”**，人工锁定是另一种约束。
- 旧项目缺少水位时按兼容约定处理，不能仅凭列表有十项判断总目标只有十章。应同时核对总目标、水位、契约和入口。
- “补齐全书规划”保持总章数不变；“延长全书”才增加总目标。两者都有模型成本，前者不能以修改结局或重写已归档章为代价。
- 渐进细化的自动触发和入口差异见 N11。不能笼统承诺“十章写完后所有入口都会后台自动续纲”。

### 自适应 2+1 与单路径

`run_adaptive_creative_exploration` 先生成两个创作方向候选，再选择；候选多样性低于 `0.55`、选择置信度低于 `0.60`、显式要求第三候选或选择结果无效时，才补一个候选并重选。通常两次模型调用，补选时最多四次（不含重试），不是固定三个模型同时写作。

候选必须服从明确输入；探索异常或没有合格选择时退回已有确定性创作包，不让可选探索拖垮初始化。单路径跳过这轮分叉探索。功能开关关闭时有兼容回退；选项名不能被理解为质量保证。

主线依赖：`输入意图 → 设定/人物 → 蓝图 → 大纲/契约 → 本章计划 → 正文 → 审校与有限修复 → 最终归档/状态 → 下一章`。研究、创意探索、记忆和全书审计服务于这条主线。

| 层次 | 权威产物/责任 | 重要边界 |
| --- | --- | --- |
| 用户输入 | 初始化请求快照、明确指令、人工编辑和锁定；`core/user_intent.py` 投影 | AI 补充内容不能伪装成用户输入；`build_user_intent_card` 消费初始化请求，裸 `StorySpec` 使用对应专用投影函数 |
| 设计 | StoryBible、CharacterBible、StyleProfile、CreativeDirectorPacket、Blueprint | 未来计划不是已发生的故事事实；主题不是每章必须复述的口号 |
| 执行依据 | Outline、ChapterDesign、Narrative/Chapter Contracts、ChapterSourceSlice | 正文阶段消费有边界的来源切片，不直接塞入全书原始蓝图泄漏后续兑现 |
| 工作版本 | Plan、Draft/WAVE、ReviewProgress、检查点、报告 | 草稿和模型建议不等于已归档正文；报告必须对应其实际检查的文本 |
| 已发生事实 | 最终正文、StoryKernel、NarrativeState、出口状态与证据 | 候选状态增量先裁决再接纳；聊天摘要、向量检索不是第二套正史 |
| 衍生产物 | 情节/表达记忆、摘要、publication projection、导出与 TTS | 失败可按各自边界恢复，不能倒过来无授权修改小说 |

入口分工：

- `workspace/execution.py` 是稳定再导出门面；实际入口在 `workspace/helpers/execution_runners.py`，手动检查点在 `workspace/sessions/`。
- NIMO 的 FastAPI → app_service/job → workspace 与 PySide/CLI 的 workspace 调用共用底层，但上层编排不同，不能推定所有回调相同。
- `app_service/book_autorun.py` 在引擎端保存连续执行状态，不是靠浏览器定时点击下一章。
- NIMO 的桌面恢复只重新读取现有 Engine 视图和运行诊断；它不派发写作任务、不改变作者授权、正文、提案或归档，也不以页面重载替代草稿恢复。
- `control_plane` 已有工作单、尝试、阶段、事件、资源版本与调度优先级。默认 advisory 的边界不能宣传为所有写入已经强制鉴权。
- 运行品质预设 compat/safe/balanced/enhanced 会组合意图守卫、研究刷新、灵感、短篇自适应修订、长篇最终复核开关；它们不是作者授权模式。

## 3. 长篇逐步行为

以下 N 编号是跨文档引用的稳定步骤 ID；不是新的运行时枚举。来源索引见第 7 节。

### N00 建项、作者意图与恢复指纹

- 入口/输入：长篇初始化表单或 CLI/API 请求；题材、基调、人物、世界、冲突、POV、开篇/结局偏好、额外要求、章数与字数等。
- 行为/输出：形成请求快照、Spec 和统一意图卡，初始化缓存与恢复按输入指纹判断新鲜度。输入已有的明确要求不由 Spec 补全改写。
- B1：未来规划及运行时来源切片统一从 `states/init_request_meta.json` 的 `request` 投影作者要求；遗留/AI 补充 Spec 仅保留为 `accepted_project_facts`，不再提升为明确输入。必需初始化确认不接受默认值、超时或仅 kind/chapter 匹配的重放，重启批准须绑定候选指纹。
- 用户操作：编辑输入、选择创意探索与规划深度；已存在项目的重初始化必须考虑原稿与输入漂移，不能静默覆盖。
- 失败/影响：输入变了就不能把旧缓存当新方案；计划、人物、正文和后续候选都要沿用适用范围内的意图约束。[C1、C2]

### N01 资料研究与事实依据

- 入口/输入：初始化研究；章级规划按配置进行事实刷新。输入来自作品范围和本章任务。
- 行为/输出：研究资料与 grounding 结果供设定、大纲和章节消费；创意灵感与事实依据用途不同。
- 用户边界：外部文档中的文字不是作者指令；模型常识不冒充已验证资料。虚构世界与明确的架空设定不由现实资料自动改写。
- 失败/影响：按现有研究配置报告可用性或降级；不能把未证实信息写成“已验证”。研究不是无预算、无限拓展的新任务。[C1、C8]

### N02 基础设定、人物与知识边界

- 依赖：StoryBible 与 BlueprintElementSelect 可并行；CharacterBible 依赖 StoryBible，再建立人物名单、档案、关系与弧线。
- 输出：世界/连续性规则、人物系统、知识边界、StyleProfile 和 EntityGraph。风格由输入推导，不套一个统一商业文风。
- 用户操作：配置启用时可在人物检查点编辑或中止；后续修改要追踪对蓝图、契约和已生成内容的影响。
- 恢复：按阶段产物和输入指纹复用；独立阶段可并行，有依赖的阶段不能为了加速读未完成状态。[C1]

### N03 创意方向与叙事蓝图

- 输入：作者意图、设定/人物/风格及元素选择。确定性创作包可叠加自适应 2+1 探索。
- 输出：CreativeDirectorPacket、全书结构/转折、人物弧线、支线、伏笔与回收安排；蓝图经过结构和语义一致性处理，不只检查 JSON 能否解析。
- 用户操作：按配置出现 concept、blueprint 检查点；模型的候选排序只是推荐。
- 失败/影响：可选探索可回退；基础蓝图不能靠牺牲明确意图来“修复成功”。蓝图是下游大纲的设计约束，不是已发生事实。[C1、C2]
- 初始化候选边界（2026-09-01 / R4）：蓝图、世界/人物圣经、实体注册和章节契约的 schema 规范化、精确 JSON 定位和本地回填统一产生隔离候选证据。模型候选与本地候选每次都从同一未修改基线开始；失败模型输出不会成为本地回填的输入。未批准的初始化中间物只有经原策略校验通过才能继续；已配置项目仍在进入此直写路径前被基础资料版本化提案守卫拦截。
- 语义编译覆盖（2026-09-02 / SC1）：不新建时间事实类型，继续使用 `CoherenceClaim`、原 claim ledger 和既有抽取/裁决 TaskType。抽取包必须声明 `complete|partial|uncertain` 及未处理来源；不完整结果按结构拆批而不按题材词表猜含义。来源、项目画像、提示词/格式合同版本和模型路由共同组成编译指纹；指纹不变时 claim 与裁决批复用，不再发起模型调用。
- 候选与批准（2026-09-02 / SC2）：模型判定的明确冲突与不确定项写入既有 `.authoring/repair_cases`，保存原始 artifacts、claims、模型理由、定位、编译指纹和来源哈希。明确冲突最多使用既有有界轮数中的三个模型候选，每个都从同一未改基线重新抽取 claims 并完成 pair 裁决；只有全部覆盖与裁决通过的未批准初始化中间物才可继续。已配置/已批准来源不直写，候选转为既有基础资料提案或 `PlanningRevision`，发布仍由原 CAS、作者批准、日志与恢复回执完成；RepairCase 仅镜像提案/回执，不是第二发布器。

### N04 分批大纲与章节设计

- 输入：全书目标、蓝图、人物与规划深度。生成大纲、章节设计矩阵，校验覆盖并按需要润色；可经过 outline 编辑检查点。
- 全书规划覆盖目标全部章节；渐进规划区分预览水位与细化水位。模型批次大小是容量策略，不是全书规模上限。
- 用户操作：查看全书/近端计划、编辑本轮方案、补齐原目标或明确延长。不能将“补齐”作为“延长”的别名。
- 失败/影响：保留有效批次供恢复；未来细化与润色使用隔离候选及严格同步，不能发布只有大纲、没有对应契约的半成品。[C1、C9]
- 章内时限质量门（2026-09-01）：分批大纲验收现复用窄范围期限提取，同一章若对「停职/受审/禁足/隔离/封锁」同时声明多个总天数，该批次作为 critical 问题进入原有有界质量重试，未验收章节不进入安全恢复点。「停职第三日」被视为进度，「三日停职结束」才被视为总期限。该规则是模型语义一致性编译器通过影子验收前的过渡安全层，禁止继续增加主体词表或数字规则，不代表已实现通用语义判断。
- 通用 claim pair（2026-09-02 / SC1）：同章或章节范围重叠的 claims 全部建立结构配对，不受候选数上限截断；同一 pair 即使被多个索引命中也只送审一次。远距依赖仍复用原语义召回。本地仅核对来源路径、claim/candidate ID、覆盖矩阵和输出完整性；已删除“阶段概括必然是无害进展”的本地语义过滤，能否同时成立交给模型。
- 作者语义决定（2026-09-02 / SC2）：不确定项可记录“可同时成立”或选定权威 claim。决定必须同时绑定精确来源哈希和完整 claim IDs；来源不变时复用且零模型询问，来源改变时旧案例自动 stale。总期限、人物命运、世界规则、身份等重大来源含义由模型标记风险，本地不猜主题；已配置项目即使处于授权自动也必须走明确批准的现有提案链。
- 模式驱动刷新（2026-09-02 / SC3）：大纲、基础设定、蓝图或契约经既有发布器提交后，共创/授权自动模式使用原 JobService 排入 `semantic_consistency`。手动模式仅显示“刷新语义一致性”，未操作不发生调用。命令只接受 project/story/policy 版本，来源路径与受影响章节由服务端从现有作品结构计算；作业仍受停止、范围、全局/作者预算和稳定模型路由限制。
- 影子许可（2026-09-02 / SC4）：在模型语义尚未成为主门禁时，来源刷新和 Plan 对照都先调用 R7a 的确定性抽样、每项目 30 日次数上限和独立预算许可。默认真实影子开关关闭且预算为 0，因而自动排到的作业只记录 `shadow_skipped`，零 provider 调用。许可后每个 source/plan 逻辑身份最多一次，结果仅追加到原 repair shadow ledger，明示 `published=false/case_state_changed=false`。

### N05 契约、初始化就绪与正史起点

- 输入：基础设计、大纲和本轮细化范围。生成 NarrativeContract、ChapterContracts，进行契约一致性与覆盖裁决，建立实体注册、StoryKernel/NarrativeState 和来源切片。
- 输出：初始化就绪产物、契约与记忆索引；渐进模式的近端契约不被误报为全书契约已齐。
- 用户操作：contracts 检查点目前主要是继续/中止，不等于所有内部字段都有可视化精细编辑。
- 失败/影响：缺关键契约或来源不能进入正文；初始化任务完成与“第一章已写完”分开。随后自动准备章节由单独编排决定。[C1、C3]
- 候选优先初始化（2026-09-01 / R4）：旧 `normalize → validate → LLM repair → local fallback` 的领域顺序保留，但规范化、LLM 修复与本地回填都绑定源哈希、精确 patch、候选哈希和原策略复验。全部候选失败时返回原始 payload 和原始报告，不让未验证结果逃逸。契约一致性的确定性修复先在副本上运行，重跑同一后置条件通过后才替换未发布工作 payload；候选、`raw/normalized/comparator` 和验证束同步保存到初始化修复记录。

### N06 本章准备与计划确认（Planning）

- 入口：`execute_prepare_chapter` 或直接 `execute_run_chapter`。先检查细化水位，再检查初始化就绪、章节前置状态、恢复/重写策略和记忆缺口。
- 输入：ChapterSourceSlice、当前正史与出口状态、适用历史证据、本章用户备注。压缩后构建 StatePacket、阅读动力窗口、Bridge 和 Plan。
- 输出：Plan 吸收 Bridge 的开场锚点，场景/输入完整性检查；手动路径保存可恢复的 plan 检查点和正史水位。
- 结构化响应边界（2026-08-29）：`guidance_requirements` 是来自 ChapterSourceSlice 的只读输入证据，不是 PLAN_CHAPTER / PLAN_CHAPTER_SCENES 的模型输出字段。跨场景引用和字面合同内的 `requirement` 只承载 source、scope、satisfaction、status、evidence、source_text_hash 六个语义字段；提示词、响应 schema 和两种规划模式保持一致。对于 prompt-only provider 把同一输入的 `requirement_id` / `text` 复制进窄语义对象的已知漂移，复用统一 task-output adapter 在严格 schema 前精准移除；其他未知字段仍拒绝。计划通过本地审计后继续由权威来源重挂完整指导清单，再持久化并供 DRAFT/WAVE/Review 消费，不让模型副本改变义务分类或作者意图。
- 耗时与反馈边界（2026-08-30）：`prepare_chapter` 的“准备与规划”包含上下文压缩、Bridge 与 Plan 三类模型任务，不是纯本地组装。实测失败运行约 390 秒中模型调用累计 378.8 秒；成功重试约 137 秒中模型调用累计 132.9 秒。本地读写、组装与审计只占余量。针对同一 3500 字章节先以 8470 token 截断再扩容的浪费，PLAN 初次容量按真实 13206-token 完整响应校准为 14336；3000 字以下与 4000 字以上分别使用 10240 / 16384 起始下限，仍受路由上限和既有预算门禁约束。提示词只重复稳定指导引用索引，权威原文继续保留在来源契约；世界规则只输出一份 `world_rule_applications`，四个 scene 派生字段由本地按 scene_id 下沉。模型生成、长度扩容、已知格式本地修正、严格校验与本地审计通过共享 Engine activity 投影显示，UI 不再把整段等待误报为本地处理。
- 流式快照语义（2026-08-30）：单个内容子流是否仍在生成、是否已校验以及可见文本是否只是截取快照，统一取自 Engine 已持久化的 `validation_status`、`text_length`、`text_truncated` 与轨迹节点状态，不再由整个 job 的 `paused/completed` 状态推断。暂停在方案决定点时，已通过后端校验的 JSON 显示“已校验/待确认”；若观测快照被截取，只展示完整长度和预览长度并保留原文诊断，不把残缺预览再次解析为“JSON 无效”，也不把它冒充完整正式结果。当前节点、关注卡、运行轨迹和节点信息复用同一展示投影；Token、耗时和尝试次数明确标为当前节点/本次调用口径。无后端校验结论的停止片段保持“待核验”，不会因暂停或流停止自动升级为正式结果。
- 流式替换边界（2026-08-31）：`StreamChunk.reset` 是同一逻辑流内的有序清空信号。Anthropic 的缓存/原生结构化降级，以及 Router 在已经输出部分内容后切换备用路由，都会先发出 reset；共享 runtime 与长篇 LLMService 先刷新旧片段证据、再清空正文/思考累加器并发出 `llm_stream_restart(reset_output=true)`，后续替代片段从零计数。最终响应、校验与持久化只使用替代流，不会把失败路由片段拼进结果。文本重试的各次 `stream_id` 不同，但共享一个 `operation_id`，NIMO 因而把旧失败轮标为已取代，而不是长期计入“需处理”。兼容 `on_delta(str)` 不能表达清空，只保留给无状态内容消费者；桌面观测和新增流消费者必须使用 `on_chunk(StreamChunk)`。
- PySide 安全投影（2026-08-31）：旧桌面现消费与 NIMO 相同的 `output_kind/validation_status/repair_source`。语法可解析的 JSON 在后端给出 `validated` 前仍标为“JSON 草稿/诊断”；`repairing/retrying/failed` 有明确状态，validated 事件中的权威快照替换原始片段。传输 reset 会清空同一流但不把替代结果标成废弃；跨轮 retry 仍保留旧轮证据并选择新轮。此调整只修正可见事实，不增加批准、写盘或 Canon 权限。
- 用户操作：重新计划、追加备注、编辑计划后写作或继续；不能用陈旧计划覆盖更新后的上游事实。
- 章台共创入口（2026-09-01）：共创是当前章台上下文的协作动作，因此入口常驻于“章台工作台”标题右侧，不进入全局顶栏、不与“叙事工具”等领域工具混排。入口位于导航动作之前，用轻量强调色与分隔线区分“对本章协作”和“离开当前工作台”。打开后同一按钮显示“收起共创”并持有 `aria-expanded/aria-controls`；关闭不导航、不重置章台。阅卷页的默认浮动入口不受影响。
- 审查证据预检（2026-08-30；2026-09-01 前移）：`upstream_compass.find_outline_plan_duration_conflicts` 区分 Plan 偏离与大纲内部冲突。前者仅回到 Plan 有界重规划；后者保留冲突短语、停在源证据修订/审批边界，不让正文迁就错误证据，也不无限重做 Plan。源大纲内部期限检查现在 `StatePacket`、上下文压缩、Bridge 和 Plan 之前运行；失败仍写入同一份精确定位报告，但不产生新 provider 调用。Engine 把 `lastFailureKind=upstream_source_conflict` 和 `recoveryTarget=manual` 作为共享恢复事实投影；NIMO 改为打开大纲共创修订，冻结 PySide 仅显示不可越过的源修订提示，两端都不再提供通用 Plan 重试/继续连跑。旧会话没有新字段时由 Engine 对已知旧错误结构做有界兼容分类，客户端不解析本地化异常文案。真实 `data/long_26bd9e6d` 第 2 章只读回放稳定提取到大纲中「停职=[3,5]」，恢复目标是源证据，不是正文。
- 预编译与章节边界（2026-09-02 / SC1–SC3）：初始化一致性报告保存 claim 覆盖、pair 覆盖、编译指纹和模型裁决。SC3 将同一 ledger 的可验证结果投影到 `ChapterSourceSlice.semantic_consistency`：`clean` 继续，`conflict` 映射 `upstream_source_conflict`，`review_required` 映射 `upstream_source_review_required`，缺失/过期/编译失败映射 `upstream_semantic_not_ready`；三者均不可以重做章节 Plan 伪装恢复，共享恢复目标为 `semantic`。准备时只核对来源指纹、ledger/report 哈希和状态，零 provider 调用；当前默认仍为影子模式，保留 SC0 fallback 主拦截。provider/schema/预算/覆盖失败记入同一 ledger，不得伪装为 clean。

- 修复恢复边界（2026-09-02 / SC2–SC3）：已验证的语义候选在工作台只能创建现有版本化规划/基础资料提案。批准本身不改来源；原 `PlanningRevision.publish` 完成原子发布后，RepairCase 才核对已提交候选哈希并记录 prepared/committed 镜像回执。发布作业只在原提案已提交后尝试排入语义刷新；排队失败不会倒置已原子提交的作品，而是将错误保存在原提案结果并投影为 failed。重试已应用提案只核对同一回执，不再写作品。

- 失败/影响：只对规划负责的冲突做有限重规划；源大纲内部冲突必须先形成并批准版本化修订，不展示“重新准备方案”。已归档后续章存在时，要按兼容/重建/外科式等重写策略处理，不能视为普通接写。已记录的旧失败保留为证据；加载新后端只更正恢复引导，不修改旧日志、大纲、正文或跳过方案确认。[C3、C4、C5]

### N07 正文生成（Generate）

- `prepare_generate_context` 组装共享上下文；DRAFT 按场景写作，只消费 scene_intent 的 20 字段子集，不带完整 voices 或 cross-scene intent。
- 可选 ChapterRepair 在 WAVE 前执行；WAVE 单次织合，消费完整 35 字段 scene_intent、人物声音和跨场景设计，形成可审校章节。
- 用户操作：通过前置计划、备注与后续检查点控制内容；“本章自动”不等于用户给每一项模型建议背书。
- 失败/恢复：WAVE 后才设置 `draft_done`；恢复据此跳过已完成的 DRAFT+WAVE。WAVE 后置诊断形成告警，不直接抛错取代 Review。
- 性能边界：有共享状态依赖的相邻章节不能靠任意并行生成获得同等连续性；已有阶段数据投影不应被全量重复上下文替代。[C4]

### N08 审校、证据与有限修复（Review）

- 输入：WAVE 正文、Plan/契约、正史与证据；包含开场守卫、对齐、连续性、章节修复审计，以及因果预计算。
- 行为：连续性/对齐修复，去重、指代、自重复及机械清理，守卫、因果、阅读动力等检查与修复；提取和评估、指导契约审计。具体启用项由配置和实际问题决定，不是每章无条件全部运行。
- 修复边界：共享总轮数预算、维度协调和回退；失败使用最后经过验证的正文，不保留“修过但复核失败”的版本。
- 证据合同（2026-08-30）：对齐输出改为稳定 `source_ref + source_evidence + coverage_status + severity + confidence + chapter_evidence`；只有高置信、源引用可验证，且冲突引文真实存在于当前正文的 `missing/conflict` 才能生成阻断项和 `RepairTicket`。`partial/uncertain/advisory` 保留为可见建议，不为了找问题而触发改文；低分但没有已核验阻断项只是诊断信号。
- 报告版本（2026-08-30）：对齐、连续性、因果、阅读力、章节修复、Critic 和编辑检查都记录当前正文哈希、聚合上游上下文哈希以及 packet/bridge/plan/大纲/来源切片/Canon/设定/风格/编辑合同等分项哈希。旧报告只有正文哈希不再复用；不同章即使文本相似也不借分。综合 Eval 继续使用它实际收到的 eval/kernel context 哈希，不用另一套虚构证据。
- 闭环与差分复审（2026-08-30）：修复候选必须对变更后精确正文重新审查，不再用高相似度绕过复审。复审优先关闭初审 ticket；新意见只有属于原源要求，或能证明是本轮修复新引入的正文冲突，才可阻断。其他新批评降为 `new_observation`，防止反复审查扩大负面清单。候选排名合并字面合同与已核验语义缺口为同级硬义务，避免修复五个真问题却因一个字面项暂缺而被回滚。
- 定位合同收敛（2026-08-31）：连续性、因果、阅读力、章节质量和全书审计进入 `prepare_findings_for_repair` 后，除原有段落锚点/readiness 外都会得到同一 `diagnose_locate_patch_verify` 投影；无锚点、重复/过期锚点、旧值哈希变化或引用/修复靶点重合都降为人工，不得扩大到全文。共享 harness 最多执行五次、默认两次候选尝试；每次从未修改输入重新开始，只保留候选摘要/哈希与验证结果。只有同一审查 lane 明确通过的候选才返回给既有发布者，harness 本身不写文件、不提交正史、不授予审批。

### N09 润色、拟人化与最终文本复核（Polish/Humanize）

- 输入：经审校的文本、问题证据和有效风格约束；润色、字数整理与拟人化是否启用由运行配置/阈值决定。
- 2026-08-30 拟人化精度核对：本地规则/模式库先只生成候选，模型分批裁判后会将证据重绑定到唯一原文跨度，可恢复错误段落序号，拒绝重复/不一致锚点，并在修补后用变更比、语义漂移、新增问题和质量回归守卫回滚。这证明局部定位/替换链路有较强保护，但不等于真实小说语料上的误报率已校准：段落定位仍以空行分段为主，且缺少面向中文小说的 precision/recall 与作者接受率基准。`humanize_score` 是加权命中指标，不是文学质量概率。
- 2026-08-30 语义误修收紧：裁判前的确定性快速路径现仅允许有界标点修复（当前为破折号超限）。`filler_phrases` 和 `significance_inflation` 命中只作为候选证据；只有模型/合并裁判明确返回 `actionable=true` 且给出可定位的具体替换时才可修补。模型拒绝、空建议或 provider 失败均只保留报告，本地重绑定不得将其重新提升为自动改文。该变更不放宽其他阈值、回归门禁或作者验收。
- 2026-08-30 卷帙拟人化阅读层：报告不再将 `pattern_hits` 按通用 JSON 表格平铺，而是按严重度呈现一基段落序号、原文证据、安全修复/人工复核边界与建议；评分、计数、文件路径和机器出处收为辅助信息。对比页的相似度收入标题行，其他通用报告也将总结/问题列表提到短指标之前；布局变更不改扫描、修补、阈值、正文或批准语义。
- 输出：候选最终文本与更新后的报告。长篇有单次终态复核等配置分支；六阶段是职责划分，不代表所有开关下都是同一条不可变调用顺序。
- 用户边界：当前有自动润色、阅读动力和风格相关策略；它们的存在不意味着已经解决了审美误判或统一作者授权。目标规则见设计文档 D04/D08。
- 失败/影响：语义变化后报告、提取结果和最终哈希必须重新对齐；不能拿润色前的高分证明润色后的正文合格。[C4、C6、C8]
- 实施约束（2026-08-30）：任何精确文本改变（包括局部字面补丁、润色或拟人化）都使旧审查证据失效；复审不再以“变化小/相似度高”复用旧分。

### N10 归档、状态提交与衍生恢复（Finalize）

- 输入：最终文本、同版报告、契约履行/承接状态与被接纳的事实增量；质量门禁通过后归档并完成状态写回。
- `ArtifactManifest` 按章节及最终文本哈希记录 final_text、reports、narrative_state、story_kernel、publication_projection、memory 等阶段，供恢复判断；不是“有 Markdown 就完成”。
- workspace 的 `_ensure_required_finalization_phases` 要求正文/报告，以及开启 narrative_state_required 时的 NarrativeState/StoryKernel 同版就绪；辅助记忆和 publication projection 不在同一必需集合中。
- B2：生命周期完成前先核验必需终结；所有入口统一调用 `complete_chapter_archive`，短锁内确认同版状态并记录 `archive_committed`，释放作品锁后处理后续工作。后续阶段按最终文本哈希复用；失败记录 pending 并显示“章节已归档，规划待重试”。Engine/PySide 不把部分已记录的终结清单误当遗留章节；无清单的旧归档仍按原正史/出口/过期检查兼容，已配置新策略时不走此兼容。
- 记忆终结按最终文本哈希避免重复执行；失败留下可补偿记录，可恢复衍生记忆，不必重新生成小说。后续章节仍需检查必需事实与上下文是否可用。
- 用户操作：在 guard 检查点选择暂停、归档、修复后归档或调整大纲后归档。最后一种当前是独立较早的调整通路，不要当作已经统一走“未来候选审批”。[C3、C4、C7]
- 归档硬门（2026-08-30）：在 Canon/章节写入前，统一 `ReviewReportService` 确保所有开启的硬报告指向终稿正文哈希和当前上游证据哈希；缺失、旧版、无上下文哈希或标记过期都 fail closed。同一终稿已在当前分支完成刷新时不重复调用刷新服务；归档仍会独立校验持久化哈希。

### N11 渐进细化与后续剧情候选

两条机制必须分开：

1. **补足执行范围**：`next_planning_horizon_target` 在 `hard-current <= 2` 且未达全书目标时，将细化水位推进最多 5 章。初始 hard=5 时，普通直接执行路径可在第 3 章后推进到 10，在第 8 章后推进到 15；不是等十章全部写完。
2. **探索/修订未来剧情**：`execute_future_planning` 按 fixed/proposal/adaptive，在幕、卷、转折或重规划触发点、预算允许时处理一个未来窗口（默认 4 章）。proposal 留候选不发布；adaptive 通过独立评审后才尝试发布；fixed 不探索。

当前入口差异（必须保留在回归测试清单中）：

| 入口 | 开始前水位补足 | 归档后的规划衔接 |
| --- | --- | --- |
| 直接 `execute_run_chapter` | `ensure_chapter_planning` | completed 且必需状态提交后，统一 `complete_chapter_archive` |
| prepare → resolve 检查点 | prepare 时有补足 | 同一归档后续入口；needs_decision 不触发补纲或下一章 |
| 引擎章节连跑 | 通过 prepare/resolve，下一章准备可兜底补足 | 复用同一归档后续入口，已跟踪的缺失/异版必需状态阻止继续 |

B3：horizon 先保存 `.authoring/planning_horizon.json` 请求，再通过已有 JobService 持久化命令派发；独立 CLI/PySide 使用同一请求同步执行。下一章准备复用请求/结果，遇到未完成任务以 `planning_wait` 释放执行名额，避免单并发死锁；连跑仅在发布成功后重查权限并继续。失败/暂停需明确重试，候选待批准不得充当正式水位，达到全书目标不再派发。NIMO 分别显示归档、预览、细化水位、任务状态及“重试本批规划”，不将其混同“延长全书”。

B3 候选可通过 `PlanningRevision.load` 在重启后重新读取，仍比较作者输入和正文版本；普通聊天、任务历史、控制面命令不参与规划 CAS。拒绝或版本冲突保留原规划与候选证据。最终候选批准交互由 B4–B5 接入，完整共创能力仍关闭。

B3 验证：74 项相关回归、105 项 API/job 消费者、611 项 Vitest、TS/mypy/架构检查通过。依赖 B2 `2e72b32a`，回退前停止任务，按批次逆序 revert，保留候选、请求和作品文件。100 章测试为离线水位模拟，不是文学质量实测；实际 UI 待 B7。

候选发布复用 `PlanningRevision`：隔离生成 → 严格同步契约/来源 → 受保护章节检查 → 输入版本比较 → 项目锁内带恢复日志发布。已细化/已归档/人工锁定范围、总目标和全局结构的保护按各入口实现检查；不能扩张为未经验证的“所有重大变更均有统一授权门禁”。

### N12 连续执行、检查点与停止

- `BookAutorunCoordinator` 持久化等待初始化、运行、重试等待、暂停、完成、失败、取消等状态；跟踪目标范围、当前章、任务、检查点和重试预算，支持引擎重启恢复。

- **现有授权缺口**：`_recommended_option` 会优先选推荐的非暂停选项；推荐为暂停时也可能选其他非暂停选项。不能把该算法描述成作者授权裁决。
- `AutoDecisionProvider` 选 default_option；`CallbackDecisionProvider` 超时后可采用默认项；预置决定也有较宽的匹配规则。强制人工确认、版本绑定和超时不批准是目标要求，并非当前所有检查点都已满足。
- NIMO 保存的 manual/suggest/auto/book_auto UI 偏好与引擎任务 chapter/book 范围并非统一领域策略。任何后续优化都要同时核对 UI、API、任务服务和恢复路径。[C3、C5、C10]
- 2026-08-30 章节清理边界：正在运行、排队、安全停止或连跑重试仍硬阻断；无 worker 的纯 `paused` 方案与对应会话产物可随本次明确清理一并作废。成功后回滚 Canon/记忆、清除该范围的暂停任务，将旧连跑恢复指针标记为已取消，NIMO 原地重拉章台与叙事上下文，不跳去阅卷页。已配置作者策略的作品仍由维护屏障拒绝旧式破坏性重写，不因按钮可见而绕过专项批准。[C3、C5、C10]
- 2026-08-30 NIMO 长任务防休眠：桌面端现以 Engine `/runtime` 每 15 秒轮询的运行/排队 worker 数为唯一执行事实，有工作时调用已有 Tauri `caffeinate` 断言；worker 切换或默认检查点退避的短空档保留 90 秒，停止/失联后自动释放。不从当前页面、进度条或客户端计时器推测任务；防休眠不代替启动/恢复授权，不扩大模型调用和正文提交权限。PySide/CLI/API 运行语义不变。[C10]
