# 根因分析：编辑契约校验阻断「4 个严重问题」

## 错误链条（已通过运行日志 + 源码交叉验证确认）

1. **任务本身成功**：`adjudicate_init_conflict_candidates` 实际跑完了（74 候选、0 问题、verdict=accept，23:07:13 完成）。
2. **真正的失败点**是紧随其后的 `derive_editorial_contract` 阶段——具体是 `_derive_and_persist_editorial_contract()` 里的本地确定性校验 `validate_editorial_contract()` 在 `init_orchestrator.py:1871` 发现有 critical 级问题，于 `:1876` 直接 `raise InitCoherenceError`。
3. 这 4 个 critical 问题全部是同一类型 `editorial_element_unknown`：契约引用了不存在的叙述要素。

## 根本原因：是架构缺陷 + 修复机制副作用，不是模型质量

### 核心发现 1：模型输出是正确的，值是后续解析被破坏的

通过逐字节比对 `model_calls/064_derive_editorial_element_directives.json`（模型原始响应）与 `reports/init_editorial_readiness.json`（校验报告）：

| 报告里的（损坏）element_id | 模型原始输出的（正确）element_id |
|---|---|
| `horror_dread_rhy:thm` | `horror_dread_rhythm` |
| `i:nformation_asymmetry` | `information_asymmetry` |
| `rela:tionship_trust_arc` | `relationship_trust_arc` |
| `edi:torial_revelation_ladder` | `editorial_revelation_ladder` |

**4 个 element_id 全部在单词中间被插入了冒号 `:`**。而且这 4 个 id 在叙述要素库 `element_defs.py` 中**真实存在**（`horror_dread_rhythm` 定义在 1192 行等），也在已保存的 `blueprint_elements_selection.json` 中。所以校验本应通过。

### 核心发现 2：模型 JSON 确实畸形（缺左引号），但这是被降级容忍的

MiniMax-M2.7-highspeed 不在 `_MINIMAX_JSON_SCHEMA_MODELS`（只有 `minimax-text-01`），所以被降级到 `prompt_only`（见 `structured_output.py:359`）。模型输出了畸形 JSON：

```
},{element_id":"horror_dread_rhythm",...   ← 缺少 key 的左引号 "
```

7/7 个 element_id 键都是 `{element_id` 而非 `{"element_id`。

### 核心发现 3：`repair_missing_colon_delimiters` 状态机误伤字符串值

`run_format_response_repair_v2` 的第一道本地修复策略是 `missing_colon_delimiter`（`orchestrator.py:274`），它调用 `repair_missing_colon_delimiters`（`json_blocks.py:367`）。该函数的状态机在遇到「key 缺左引号」这种它未建模的畸形时，状态失步，在值字符串**内部**错误插入了 `:`（如 `rhy:thm`）。

现有测试 `tests/unit/test_repair_missing_colon.py:79` 的 `test_string_value_not_corrupted` 只验证「不崩溃」，没断言值不被破坏——这个回归洞直接放行了本次损坏。

### 核心发现 4：修复机制不完善——编辑契约是唯一没有修复回路的 init 门

`init_orchestrator.py` 里其他所有 init 产物（blueprint 1673-1815、outline 2310-2437、narrative contract）都包在 `while True` 修复回路里：`run_init_coherence_v2_gate → _init_coherence_blocks → _init_coherence_repair_stop_decision → _repair_init_artifact_payload`，耗尽轮次才 raise。

唯独 `_derive_and_persist_editorial_contract()`（1827-1915）是**一次性生成 + 一次性校验 + 立即 raise**，没有 `run_init_coherence_v2_gate`、没有 `_repair_init_artifact_payload`、没有 fallback、没有 try/except。所以一次解析副作用就直接判死整个立项（已跑 32 分钟的工作全部丢弃）。

## 修复方案（上下游两层）

### 上游修复（治本）：阻断损坏来源

**A. 让 `repair_missing_colon_delimiters` 不破坏字符串值**
- `json_blocks.py:367`：当 `string_role` 不确定或 key 左引号缺失时，应让该候选失败（raise），让 orchestrator 回退到下一策略 `safe_parse_json`，而不是在值里插 `:`。
- 补强 `tests/unit/test_repair_missing_colon.py`：新增「key 缺左引号」场景，断言值不被破坏、函数返回未改动原文或抛错。

**B. 编辑契约生成时把可选 element_id 白名单注入 prompt 并做后处理约束**
- `editorial_contract_step.py:_normalize_element_directives`（499 行）：对每个 `element_id` 做一次「已知库 ID 」的最小标准化（去除误插的 `:`、空白），若仍不在库则保留原值让校验如实报错。这是防御层，不掩盖真实问题。

### 下游修复（治本）：补齐编辑契约的修复回路

**C. 给 `_derive_and_persist_editorial_contract` 加修复回路**
- 参照 blueprint 回路（1673-1815）：用 `while True` 包住 `EditorialContractStep.run` + `validate_editorial_contract`，critical 时调用 `_repair_init_artifact_payload`（需在 `init_coherence.py` 的 `_ARTIFACT_ALIASES`/`_LIST_KEY_BY_ARTIFACT` 注册 `editorial_contract`），受 `_init_coherence_max_repair_rounds`（默认 2，上限 3）约束，耗尽才 raise。
- 这样即使偶发解析损坏，也能自动重生成或修复，而不是直接判死。

**D. 把 `InitCoherenceError` 的 readiness 报告落盘位置对齐**
- 当前 critical 分支在 1872-1875 已存了 `init_editorial_readiness.json`，回路化后应统一走 `_save_init_readiness`，保持与 blueprint/outline 一致的事件轨迹。

### 不建议的修复
- 不要为了「避免冒号」而给 MiniMax 关掉 JSON 修复整体——那会让更多任务直接报 JSONDecodeError 失败。
- 不要把 `editorial_element_unknown` 降级为非 critical——它本来是真实保护（防止契约引用幻觉要素），只是这次撞上了损坏假阳性。

## 验证计划
1. 新增单测：`test_repair_missing_colon.py` 增加「key 缺左引号」场景，断言 `horror_dread_rhythm` 不被改成 `rhy:thm`。
2. 新增单测：`repair_missing_colon_delimiters` 对畸形输入要么不改动、要么抛错，绝不在值里插冒号。
3. 用本 run 的 064 原始响应内容做回归：修复后应解析出正确的 `horror_dread_rhythm`。
4. 跑 `tests/unit/ -n auto -q` 与 `ruff check novel_forge/ tests/` 确认无回归。

## 结论
这是**架构缺陷 + 修复机制副作用**的复合问题：`repair_missing_colon_delimiters` 有值损坏回归洞（治本点 A），且编辑契约门缺失其他 init 产物都有的修复回路（治本点 C）。模型质量只是诱因（输出畸形 JSON），但单次模型缺陷本不该判死整个立项。建议两层都修。
